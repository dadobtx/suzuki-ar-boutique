CONTEXTO

El catálogo de demo fue reemplazado por el catálogo real de la boutique: 10 prendas
con número de parte Suzuki (990F0-XXXXX) como id y sku, precio real y tallas reales.
Las imágenes nuevas son PNG de 2048x2048 con fondo blanco, y cada prenda tiene además
un thumbnail de 512px (<PN>.thumb.png) y sus anchors (<PN>.anchors.json).

Una de las prendas, la 990F0-BKQJ5 (Team Black Reversible Jacket), es REVERSIBLE:
tiene cara roja y cara negra. Es UN SOLO producto con UN SOLO número de parte, no dos
productos. Los assets de las dos caras ya están en public/garments/:

  990F0-BKQJ5.png / .anchors.json / .thumb.png     -> cara ROJA (la de por defecto)
  990F0-BKQJ5_2.png / .anchors.json / .thumb.png   -> cara NEGRA

public/catalog.json YA TIENE los datos: la entrada de 990F0-BKQJ5 lleva un array
"variants" con las dos caras (id, label, color, overlayUrl, anchorsUrl, thumbnailUrl),
y los campos overlayUrl/anchorsUrl/thumbnailUrl de la prenda siguen apuntando a la
cara roja (la variante por defecto). NO hay que tocar catalog.json.

OBJETIVO: que el cliente, con la prenda reversible activa, pueda elegir con un toque
qué cara se prueba, y que ese cambio afecte a los TRES caminos de prueba: el overlay
AR, la foto con FASHN y el live con Lucy 2.

PROBLEMA DE FONDO QUE HAY QUE ARREGLAR PRIMERO
=====================================================================
Hoy el código NO respeta los campos de assets del catálogo: arma las rutas a partir
del sku. Mientras siga así, una variante es imposible (las dos caras tienen el mismo
sku). Estos son los puntos exactos:

1. src/hooks/useGarmentRenderer.ts, líneas ~53 y ~55:
     image.src = `${base}garments/${garment.sku}.png`;
     fetch(`${base}garments/${garment.sku}.anchors.json`)
   Además el caché (garmentCache, loadingSkus, activeSkuRef) está indexado por
   garment.sku — con variantes eso devolvería la imagen equivocada desde caché.

2. src/lib/liveTryon.ts, línea ~127 (sendGarment):
     reference_image_url: `https://dadobtx.github.io/suzuki-ar-boutique/garments/${sku}.png`
   Arma la URL pública desde el sku y además tiene el origen de producción hardcodeado.

3. src/components/catalog/CatalogCard.tsx, línea ~28:
     const imageUrl = `${baseUrl}${garment.overlayUrl.replace(/^\//, '')}`;
   Usa el overlay de 2048px (1 a 4 MB por prenda) para la tarjeta del catálogo,
   ignorando thumbnailUrl. Hay que usar el thumbnail.

4. src/components/kiosk/AIProcessing.tsx, línea ~78: este SÍ usa
   activeGarment.overlayUrl — está bien, solo hay que pasarlo por el resolver nuevo.

   *  overlayUrl/anchorsUrl/thumbnailUrl de la prenda. */

--- 2) Resolver de assets: src/lib/garment-assets.ts (ARCHIVO NUEVO) ---
Módulo puro, sin React, fácil de testear:

  export interface ResolvedGarmentAssets {
    /** Clave de caché: sku, o `${sku}#${variantId}` si hay variante */
    key: string;
    overlayUrl: string;
    anchorsUrl: string;
    thumbnailUrl: string;
    variant: GarmentVariant | null;
  }

  export function resolveGarmentAssets(
    garment: Garment,
    variantId?: string | null,
  ): ResolvedGarmentAssets

Reglas:
 - Sin variants, o variants vacío -> usa overlayUrl / anchorsUrl / thumbnailUrl de la
   prenda, thumbnailUrl cae a overlayUrl si viene undefined, key = garment.sku,
   variant = null.
 - Con variants: si variantId es null/undefined o no existe en la lista, usa
   variants[0] (NO tirar error, el kiosko no debe quedarse sin prenda por un id malo).
 - key = `${garment.sku}#${variante.id}`.
